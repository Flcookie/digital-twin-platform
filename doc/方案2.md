## 2. Key Problems Identified

### 2.1 MQTT Event Out-of-Order Issue

**Problem:**
- MQTT guarantees order only for messages from **same client to same topic**
- Current system has **multiple clients** (stations) sending to same topic `component_event`
- Network delay can cause events to arrive out of order
- Example: Station A sends "TRANSFER" at T1, Station B sends "BLOCK" at T2, but B's event arrives first

**Current Solution Limitations:**
- 300ms time window buffer
- Periodic flush every 0.3s
- May miss events if MQTT delay > 300ms
- No mechanism to determine when buffered events are "safe" to process

**Root Cause:**
- Lack of event-driven trigger mechanism
- Relying on fixed time window without considering latest received event timestamp

---

### 2.2 Event Cache Update Mechanism

**Problem:**
- Current: Periodic flush every 0.3s (`time.sleep(0.3)` in `main_service.py:104`)
- Issue: Does not utilize information from newly received events
- Inefficient: May process too early or wait too long

**Requirements:**
- Should be **event-driven**: when receiving a new event, determine which buffered events can now be confirmed
- Buffer should maintain sorted order by timestamp
- Use latest event timestamp to determine cutoff point for flush

---

### 2.3 Graph Database Event Ordering

**Current Implementation (`neo4j_writer.py`):**
- Only creates DF (directly follows) edges between consecutive events of **same part**
- Events stored in Set (unordered) in graph database
- Retrieving events requires reading all nodes then sorting by timestamp (O(n log n))

**Problem:**
- Process Mining focuses on **single case ID** (single part)
- Our system needs to track **system-level events** (multiple parts simultaneously)
- Need to know order between events of **different parts** at same/similar timestamps

**Teacher's Suggestion:**
- Create a global event ordering chain, not just per-part
- Each event has a "next" relationship to form a total order
- Benefits:
  - Fast retrieval using depth-first search (O(n) linear)
  - No need to sort after reading from database
  - Enables efficient streaming process mining

**Implementation Approach:**
- Maintain a "latest_event_id" pointer globally
- When writing new event to Neo4j:
  1. Create event node
  2. Create DF edge to same part's previous event (existing logic)
  3. **Create NEXT edge from global previous event** (new logic)
  4. Update global latest_event_id

## 3. Proposed Solutions

### 3.1 Event-Driven Buffer Flush Mechanism

**Concept:**
When receiving a new event with timestamp T_new:
1. Add event to buffer (existing: bisect insert)
2. Determine cutoff = T_new - window_ms
3. Flush all events with timestamp < cutoff
4. These events are "safe" because even if delayed events arrive, they would be < cutoff - window_ms

**Implementation Changes in `event_buffer.py`:**

```python
class EventBuffer:
    def __init__(self, window_ms: int = 300, max_size: int | None = None):
        self.window_ms = window_ms
        self._events = []  # (ts, event) sorted by ts
        self._lock = threading.Lock()

    def add_and_flush(self, event: dict) -> list[dict]:
        """
        Add event and return events that are now safe to process.
        Event-driven: uses new event's timestamp to determine cutoff.
        """
        time_str = event.get("time")
        if not time_str:
            return []

        ts = parse_time_to_float(time_str)
        item = (ts, event)

        with self._lock:
            # Insert new event
            bisect.insort(self._events, item)

            # Determine cutoff based on latest event timestamp
            # Find the maximum timestamp in buffer (should be the last one)
            if not self._events:
                return []

            max_ts = self._events[-1][0]  # Latest event timestamp
            cutoff = max_ts - (self.window_ms / 1000.0)

            # Flush events older than cutoff
            ready = []
            while self._events and self._events[0][0] < cutoff:
                _, ev = self._events.pop(0)
                ready.append(ev)

            return ready
```

**Changes in `main_service.py`:**

```python
# OLD:

# In main loop:
```

**Benefits:**
- **Event-driven**: No arbitrary sleep intervals
- **Faster response**: Events processed as soon as safe
- **More accurate**: Uses actual event timestamps, not wall clock
- **Simpler main loop**: No need to periodically check buffer

### 3.2 Global Event Ordering in Neo4j

**Goal:** Create a total order of all events, not just per-part ordering.

**Implementation in `neo4j_writer.py`:**

```python
# Add global state
_last_event_per_part: dict[str, str] = {}  # Existing
_last_global_event_id: str | None = None    # NEW

def write_event_to_graph(event: dict):
    """Write one event to Neo4j with both per-part and global ordering."""
    if "time" in event and "timestamp" not in event:
        event = _to_neo4j_format(event)
        if event is None:
            return

    event_id = str(uuid.uuid4())
    part_id = event["part_id"]

    with driver.session() as session:
        # Create event node
        session.execute_write(_create_event_tx, event_id, event)

        # DF edge: same part's consecutive events (existing)
        previous_part_id = _last_event_per_part.get(part_id)
        if previous_part_id is not None:
            session.execute_write(_create_df_tx, previous_part_id, event_id)

        # NEXT edge: global event ordering (NEW)
        global _last_global_event_id
        if _last_global_event_id is not None:
            session.execute_write(_create_next_tx, _last_global_event_id, event_id)

        _last_global_event_id = event_id

    _last_event_per_part[part_id] = event_id

def _create_next_tx(tx, previous_id, current_id):
    """Create NEXT edge for global event ordering."""
    query = """
    MATCH (e1:Event {id: $previous_id})
    MATCH (e2:Event {id: $current_id})
    MERGE (e1)-[:NEXT]->(e2)
    """
    tx.run(query, previous_id=previous_id, current_id=current_id)
```

**Graph Structure:**
```
Event1 --DF--> Event2 --DF--> Event3  (same part p1)
  |              |              |
  NEXT          NEXT           NEXT
  |              |              |
  v              v              v
Event4 ------DF-----> Event5           (same part p2)
```

**Query for All Events in Order:**
```cypher
// Find first event (no incoming NEXT)
MATCH (e:Event)
WHERE NOT exists((e)<-[:NEXT]-())
RETURN e
ORDER BY e.timestamp LIMIT 1

// Traverse all events via NEXT
MATCH path = (start:Event)-[:NEXT*]->(end:Event)
WHERE NOT exists((start)<-[:NEXT]-())
RETURN nodes(path)
```

**Benefits:**
- Linear traversal O(n) vs sorting O(n log n)
- Preserves insertion order (which respects buffer sorting)
- Enables efficient streaming queries
- Supports both per-part (DF) and system-level (NEXT) analysis

**Caution:**
- If system restarts, need to handle finding the last global event
- Could add a "Session" node to mark different runs

```python
from fastapi import FastAPI, WebSocket
from fastapi.staticfiles import StaticFiles
from fastapi.responses import HTMLResponse
import asyncio
import json
import paho.mqtt.client as mqtt
from neo4j import GraphDatabase
import common

app = FastAPI()
app.mount("/static", StaticFiles(directory="static"), name="static")

CONFIG = common.load_json("config.json")
neo4j_driver = GraphDatabase.driver(
    CONFIG["neo4j"]["uri"],
    auth=(CONFIG["neo4j"]["username"], CONFIG["neo4j"]["password"])
)
MQTT_BROKER_HOST = CONFIG["mqtt_broker_host"]
MQTT_BROKER_PORT = CONFIG["mqtt_broker_port"]

_latest_kpi = {}

def on_connect_kpi(client, userdata, flags, rc):
    print("[web_api] Connected to MQTT for KPI (rc={})".format(rc))
    topic = common.render_topic("kpi", "main_service", "all")
    client.subscribe(topic, qos=0)

def on_message_kpi(client, userdata, msg):
    global _latest_kpi
    try:
        _latest_kpi = common.deserialize_object(msg.payload.decode("utf-8"))
    except Exception as e:
        print("[web_api] KPI parse error:", e)

mqtt_kpi_client = mqtt.Client()
mqtt_kpi_client.on_connect = on_connect_kpi
mqtt_kpi_client.on_message = on_message_kpi
mqtt_kpi_client.connect(MQTT_BROKER_HOST, port=MQTT_BROKER_PORT)
mqtt_kpi_client.loop_start()

@app.get("/")
def index():
    with open("static/index.html") as f:
        return HTMLResponse(f.read())

@app.websocket("/ws/kpi")
async def websocket_kpi(websocket: WebSocket):
    await websocket.accept()
    try:
        while True:
            if _latest_kpi:
                await websocket.send_json(_latest_kpi)
            await asyncio.sleep(2)
    except Exception as e:
        print("[web_api] WebSocket error:", e)

@app.get("/api/graph")
def get_process_graph():
    """Return process graph data from Neo4j (activity-to-activity DF)."""
    with neo4j_driver.session() as session:
        result = session.run("""
            MATCH (e1:Event)-[:DF]->(e2:Event)
            MATCH (e1)-[:OF_ACTIVITY]->(a1:Activity)
            MATCH (e2)-[:OF_ACTIVITY]->(a2:Activity)
            RETURN a1.name AS from_activity, a2.name AS to_activity, count(*) AS count
            ORDER BY count DESC
            LIMIT 50
        """)
        edges = [{"from": r["from_activity"], "to": r["to_activity"], "count": r["count"]}
                 for r in result]
    return {"edges": edges}

@app.on_event("shutdown")
def shutdown():
    mqtt_kpi_client.loop_stop()
    mqtt_kpi_client.disconnect()
    neo4j_driver.close()
```

## 8. Risk Mitigation

### 8.1 Event Loss
**Risk:** Event-driven buffer might lose events if exception occurs in callback

**Mitigation:**
- Wrap event processing in try-except
- Log all errors with event details
- Implement dead-letter queue for failed events
- Add metrics for processed/failed events

### 8.2 Neo4j Performance
**Risk:** NEXT edge creation might slow down writes

**Mitigation:**
- Batch writes if needed
- Index Event.id and Event.timestamp
- Monitor write latency
- Consider async writes (but maintain order)

### 8.3 UI Blocking
**Risk:** WebSocket or MQTT subscription might block FastAPI event loop

**Mitigation:**
- MQTT uses `loop_start()` in separate thread; FastAPI runs async
- Keep KPI snapshot lightweight (no heavy computation)
- WebSocket push every 2s is non-blocking
- Separate web_api process from main_service

### 8.4 MQTT Message Loss
**Risk:** QoS 2 might have performance overhead

**Mitigation:**
- Benchmark QoS 0, 1, 2 performance
- Consider QoS 1 if acceptable (at-least-once delivery)
- Add message ID and deduplication if needed

### 8.5 Thread Safety (MQTT Callback)
**Risk:** `on_message` runs in MQTT thread; `kpi.on_event()` and Neo4j writes may have race conditions

**Mitigation:**
- See Section 15.1 for details
- Use `queue.Queue` to pass events to main thread, or add locks in KPI calculator
- Verify Neo4j driver usage is thread-safe

### 13.6 Event-Driven Design (Teacher's Key Insight)

**Current Approach (Problematic):**
```python
while True:
    time.sleep(0.3)  # Arbitrary wait
    flush_ready(now())  # Uses wall clock
```

**Teacher's Recommended:**
```python
def on_message(msg):
    event = parse(msg)
    buffer.add(event)

    # Key: Use event timestamp!
    cutoff = event['timestamp'] - window_ms
    ready_events = buffer.flush_before(cutoff)

    for e in ready_events:
        process(e)
```

**Why Superior:**
- No arbitrary sleep
- Uses actual event time
- Processes as fast as events arrive
- Respects causality

**Mathematical Guarantee:**
```
If:
  - MQTT max delay = D ms
  - Window = W ms (W > D)
  - Receive event E with timestamp T

Then:
  Any event with timestamp < T - W
  was generated ≥W ms ago
  and should have arrived already
  → Safe to process!
```

## 15. Implementation Considerations and Supplements

*This section supplements the plan with implementation details identified during review.*

### 15.1 Thread Safety for Event Processing in Callback

**Context:** When processing events in `on_message` callback, paho-mqtt invokes the callback in its **own thread**. Both `neo4j_writer.write_event_to_graph()` and `kpi.on_event()` will run in that thread.

**Considerations:**
- **Neo4j driver:** The official Python driver is generally thread-safe for session/transaction usage. Ensure one session per write or use connection pooling correctly.
- **KPI calculator:** Review `kpi_calculator.py` for thread safety. If `on_event()` modifies shared state (counters, lists, dicts) without locks, add `threading.Lock()` protection or use a `queue.Queue` to pass events to the main thread for processing.

**Recommended approach if KPI is not thread-safe:**
```python
# In main_service.py: use a queue, process in main loop
import queue
event_queue = queue.Queue()

def on_message(client, userdata, msg):
    # ... parse event ...
    ready_events = buffer.add_and_flush(event)
    for ev in ready_events:
        event_queue.put(ev)

# Main loop (runs in main thread):
while True:
    try:
        while True:
            ev = event_queue.get_nowait()
            neo4j_writer.write_event_to_graph(ev)
            kpi.on_event(ev)
    except queue.Empty:
        pass
    time.sleep(2.0)
    # ... print KPI ...
```

**Alternative:** Add locks inside `kpi_calculator.py` if modifying it is acceptable.

---

### 15.2 UI and main_service Process Separation (KPI Sharing)

**Context:** The plan uses **independent processes**: `main_service.py` and `web_api.py` (FastAPI). KPI data must be shared across processes.

**Options for cross-process KPI sharing:**

| Option | Pros | Cons |
|--------|------|------|
| **A. MQTT publish** | Real-time, uses existing broker | Requires main_service to publish |
| **B. JSON file** | Simple, no extra deps | File I/O, polling delay |
| **C. Redis/Socket** | Real-time, scalable | Extra dependency/infrastructure |

**Recommended for Phase 3:** Use **MQTT publish** (primary):
- `main_service.py` publishes KPI to topic `kpi/main_service/all` every 2 seconds
- `web_api.py` subscribes and forwards to WebSocket clients

**Fallback (simplest):** Use **JSON file** if MQTT is not preferred:
- `main_service.py` writes `kpi_snapshot.json` every 2 seconds
- `web_api.py` reads the file on interval and pushes via WebSocket

### 15.3 WebSocket Push Interval

**Note:** WebSocket pushes every 2 seconds (`asyncio.sleep(2)`). This matches main_service KPI print interval. For higher frequency, reduce both intervals; ensure main_service does not publish faster than it computes.
